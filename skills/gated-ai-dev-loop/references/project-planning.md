## 适用条件

`Project` 是工作规模，不是新的 CLI 模式。命中任一情况时使用 `Full · Project · 主要变更类型`：

- 用户要求从零到可验收结果的完整系统、平台、应用或大模块开发；
- 需求包含多个可以独立验收的里程碑、业务域或工作流；
- 多个服务、客户端、数据层、基础设施或发布阶段必须按依赖顺序集成；
- 单一实现轮次无法安全覆盖全部需求和验收；
- 用户明确要求总体方案、路线图、阶段交付或完整项目计划。

不要因为任务使用 Full 就自动判为大型项目。单个高风险 API、迁移或权限改动仍可使用普通 Full。

## 规划产物

在用户确认基线前建立：

1. 根级 `development-overview.md`：面向人的稳定开发总纲；
2. `rounds/planning/project-plan.md`：详细里程碑、工作流、原子任务、依赖与验收映射；
3. 根级 `progress.md`：实时任务与 SOP 状态；
4. Full `baseline.md`、`tasks.json` 和 `acceptance.json`：唯一冻结开发授权。

总纲和项目计划不能取代基线。发生冲突时以用户确认并冻结的基线为准；规划必须修正到与基线一致后才能继续。

## 分层拆解

使用四层标识，禁止混用：

- `M-NNN` Milestone：用户可观察的阶段成果；
- `W-NNN` Workstream：围绕一个业务域、组件或集成目标的工作流；
- `T-NNN` Executable Task：一个开发上下文能够实现并独立验证的最小交付任务；
- `S-NNN` SOP Step：恢复、分析、确认、冻结、授权、派遣、门禁、验收和反馈处理等流程步骤。

每个 `T-NNN` 至少写明：

- 所属 M/W；
- 关联 R/A；
- 目标工作区和仓库相对允许路径；
- `dependsOn`；
- 输入、输出和对外契约；
- 测试 argv 或由哪个集成门禁覆盖；
- 可观察的完成定义；
- 主要风险和阻断条件。

一个任务如果同时跨越多个不可独立回滚的目标、包含未解决设计决策，或无法给出单独完成证据，就继续拆分。不要按“前端一个任务、后端一个任务”机械拆分；优先按可验收的纵向成果和真实依赖拆分。

## 拆解质量门禁

请求用户确认基线前逐项检查：

- 每个 R 都被至少一个 A 和 T 覆盖；
- 每个 A 都有可运行门禁或明确人工观察点；
- 每个 T 都属于一个 M/W，并有单一可观察结果；
- 每个写入任务都绑定工作区和允许路径；
- 所有提供方/消费方、数据、契约和集成依赖均有方向；
- 依赖图无环，关键路径和可并行项有事实依据；
- 每个里程碑都有进入条件、完成门禁和失败后的处理；
- 风险、未决选项和外部前置条件已经解决或明确阻断；
- `development-overview.md`、`project-plan.md`、baseline、tasks 和 acceptance 互相一致；
- `progress.md` 已初始化全部 M/W/T 和 SOP 行。

任一项不满足时保持 `WAITING_FOR_REQUIREMENT_CONFIRMATION`，列出缺口，不进入开发方式选择。

## 执行与回写

宿主是进度文件唯一写入者。每次状态变化按以下顺序执行：

1. 先持久化真实证据或阻断事实；
2. 立即更新 `progress.md` 对应 M/W/T 或 S 行；
3. 更新完成计数、当前阶段、下一责任方和阻断项；
4. 向时间线追加一条带时间和证据链接的事件；
5. 再派遣下一任务或向用户报告。

不得把开发 Agent 的“已完成”直接写成 `VERIFIED`。开发结果存在时标记 `IMPLEMENTED`；机械和语义证据通过后标记 `VERIFIED`；用户最终接受后才完成整个项目。

进度写回失败时，不得口头宣称状态已经推进。先重试安全写回；仍失败则停止并报告 `PROGRESS_WRITE_FAILED`。

## 变更控制

- 计划细化但不改变冻结授权：更新 `project-plan.md`，在 progress 时间线记录原因和影响，不删除旧证据；
- 调整任务顺序或责任方：重新检查依赖、路径互斥和工作区覆盖；
- 新增行为、验收、工作区或里程碑：不是普通计划更新，按 `REVISE_CURRENT` 重新确认；
- 删除或延期冻结范围：取得用户确认并记录 disposition；
- 创建 follow-up：保留原项目进度和证据，显式记录关系。
