## 三个独立维度

不要把风险、规模、改动性质或执行并发混成一种模式：

| 维度 | 可选值 | 回答的问题 |
| --- | --- | --- |
| 门禁等级 | None / Light / Full | 需要多严格的冻结、证据和验收？ |
| 工作规模 | Micro / Task / Capability / Project | 需要多细的计划、拆解和进度？ |
| 变更类型 | Feature / Bugfix / Refactor / Migration / Maintenance / Docs / Test | 主要在做什么性质的改动？ |
| 执行拓扑 | single / parallel | 冻结后由几个隔离开发上下文执行？ |
| 生命周期路由 | repair / revise / suggestion / new-task | 人工验收反馈如何续接？ |

Git 提交类型只能作为“变更类型”的参考，不能决定工作规模。一个 Project 可以包含多个 Capability、Task 和提交；一个 Capability 也可能同时包含 Feature、Bugfix 和 Test 工作。

## 门禁等级

- `None`：只回答、解释、诊断或审查，不写文件；不分配工作规模。
- `Light`：只允许低风险 `Micro`，影响明确、最多三个普通文件且不命中任何 Full 硬条件。
- `Full`：命中任一 Full 硬条件，或者工作规模达到 Task、Capability、Project；也允许高风险的 `Full + Micro`。

门禁等级由风险和授权强度决定，不由“看起来代码很少”决定。

## 工作规模与代表说明

| 工作规模 | 中文显示 | 固定代表说明 | 结构判定 | 代表示例 |
| --- | --- | --- | --- | --- |
| `Micro` | 微改 | 修改一个局部点，不形成独立功能包 | 单一局部行为；无跨组件依赖；一组局部测试可证明 | 修正字段映射、文案、空值处理或一个局部判断 |
| `Task` | 单任务 | 交付一个可独立验收的结果 | 一个主要验收目标；可涉及多个文件或高风险逻辑；不需要内部工作流或里程碑 | 给一个查询接口增加权限与对应测试 |
| `Capability` | 完整能力 | 多个任务协同形成一项完整业务能力 | 只有一个能力级交付与聚合验收边界；可包含多个 T、组件或服务 | 订单、库存与通知组件共同交付“订单履约”能力 |
| `Project` | 完整项目 | 多个能力和里程碑组成一个完整项目 | 完整系统/平台/应用/大模块交付，或包含多个独立能力、用户可验收里程碑、阶段交付或发布边界 | 账号、订单、结算与报表组成的业务管理平台 |

“代表说明”使用上表固定短句，必须写入 `development-overview.md` 和 `progress.md`。同时补充一条当前任务的具体说明，不能只写枚举名。

工作规模 `Task` 表示一个交付边界，不等同于基线中的单个 `T-NNN`。它通常对应一个或少量共同服务于同一验收结果的 T；一旦需要多个工作流或聚合验收，应升级为 `Capability`。

## 工作规模事实卡与判定规则

在选择 `Task`、`Capability` 或 `Project` 前，先生成一份人可读的“工作规模判定记录”。不要从需求标题是单数、用户只说了一个模块名，或接口/文件数量直接猜规模。先把一个看似单一的大需求拆成可验证的交付结构，再套用规则。

至少记录以下事实；值未知时明确写“未知”，不得留空：

| 事实 | 必须回答的问题 |
| --- | --- |
| 交付对象 | 局部点、单一结果、完整能力、完整系统/平台/应用/大模块中的哪一种？ |
| 完整交付 | 是否从现状一直交付到该对象整体可验收？用户是否已经明确确认？ |
| 独立能力 | 有哪些各自具有用户可观察结果、可单独通过或失败验收的能力组？ |
| 验收与里程碑 | 是一个聚合验收，还是存在多个用户可验收阶段、发布或回滚边界？ |
| 工作流与依赖 | 各 `W-NNN` 属于同一能力的内部实现，还是不同能力/阶段？提供方到消费方如何依赖？ |
| 实施波次 | 多波次只是内部开发安排，还是用户可观察的阶段交付？ |
| 单轮安全性 | 单一实现与验收轮次能否安全覆盖全部范围？不能时缺少什么阶段门禁？ |
| 中性信号 | 接口数、文件数、服务数以及公共契约、状态机、幂等等 Full 风险信号分别是什么？ |
| 缺失事实 | 哪些未知项会改变 Capability/Project 结论？ |

“独立能力”必须同时具有用户或调用方可观察结果和独立验收边界。公共契约、持久化、状态机、幂等、测试、部署等技术层本身不自动算一个能力；如果它们分别承载独立结果和阶段门禁，则可以成为不同能力或里程碑的组成部分。内部 Agent 分组、代码提交或开发波次不等于用户里程碑。

按以下稳定规则判定，并把命中规则 ID 写入判定记录：

- `WS-P01`：用户明确确认要从现状完整交付一个系统、平台、应用或大模块直到整体可验收，使用 `Project`。在请求冻结确认前仍须把它分解为能力组与里程碑；无法形成可执行分解时保持 `WAITING_FOR_REQUIREMENT_CONFIRMATION`。
- `WS-P02`：存在至少两个各自具有可观察结果和独立验收边界的完整能力，使用 `Project`。
- `WS-P03`：存在至少两个用户可验收里程碑、阶段交付、发布或独立回滚边界，使用 `Project`。
- `WS-P04`：用户明确要求用项目级总体方案、路线图和阶段交付治理整项交付，使用 `Project`。
- `WS-P05`：已出现完整大模块、多能力或多阶段等强 Project 信号，但决定性事实仍未知时，暂按 `Project` 规划并保持 `WAITING_FOR_REQUIREMENT_CONFIRMATION`；列出缺口，不得向下猜成 `Capability` 或冻结。
- `WS-C01`：只有一个完整业务能力、一个能力级聚合验收/发布边界，全部工作流都是该能力的内部实现，并且已明确证明未命中 `WS-P01` 至 `WS-P04`，使用 `Capability`。
- `WS-T01`：只有一个可独立验收结果，不需要内部工作流、组件集成或能力级聚合门禁，使用 `Task`。

最终选择 `Capability` 前必须明确写出：不是完整大模块交付、只有一个独立能力、没有独立里程碑/发布边界、只有一个聚合验收，并逐项排除 `WS-P01` 至 `WS-P04`。任一关键事实未知且已有强 Project 信号时使用 `WS-P05`，不能用“看起来是一个业务目标”代替证明。

接口数、文件数、服务数、仓库数、公共契约、状态机、事务、幂等、内部工作流数和开发波次数都是复核信号，不是单独的 Project 充分条件。它们可以强制 `Full`，也可以帮助发现多个能力或里程碑，但必须经过上述映射才能改变工作规模。

## 规模边界判断

按顺序判断：

1. 不写文件：门禁等级 `None`，工作规模记为 `N/A`；
2. 只是一个局部点、没有跨组件依赖：`Micro`；
3. 命中 `WS-T01`：`Task`；
4. 完整事实卡证明命中 `WS-C01`：`Capability`；
5. 命中 `WS-P01` 至 `WS-P04`：`Project`；出现强信号但事实未知时按 `WS-P05` 暂定 `Project` 并等待确认。

规模依据交付对象、独立能力、验收边界和依赖结构，不依据工期、代码行数、模型主观难度或 Git 提交数量。多个文件不自动成为 Capability；多个服务也不自动成为 Project；一个需求名称也不自动只代表一个 Capability。

以下信号用于复核边界：

- 是否存在一个还是多个用户可观察结果；
- 是否必须拆成多个能独立验证的 T；
- 是否存在提供方/消费方或组件集成门禁；
- 是否需要 M/W/T 分层、阶段验收、发布或独立回滚边界；
- 是否需要多个开发波次才能保持依赖和回滚安全。

无法确定时按 `WS-P05` 选择较大的规模、展示缺失事实并等待确认；不得用较小规模减少必要规划。

## 变更类型

变更类型只描述主要工作性质，不改变门禁和规模判定：

| 类型 | 代表说明 |
| --- | --- |
| `Feature` | 新增用户或系统可观察行为 |
| `Bugfix` | 修复已经承诺但未满足的行为 |
| `Refactor` | 保持外部行为不变地改善内部结构 |
| `Migration` | 改变数据、配置、依赖、协议或版本并处理兼容/回退 |
| `Maintenance` | 依赖升级、构建、工具链、运维或常规维护 |
| `Docs` | 只修改文档或说明 |
| `Test` | 只补充或调整测试，不改变生产行为 |

只记录一个主要类型；其他性质写在说明中。类型不能替代 R/A/T，也不能据此生成 Git commit、提交或发布动作。

## 展示与落盘

写入任务在首次路由、需求确认和每次恢复时展示：

```text
门禁等级：Full
工作规模：Capability（完整能力）
规模代表说明：多个任务协同形成一项完整业务能力
当前任务说明：订单、库存与通知组件共同交付订单履约能力
规模判定规则：WS-C01
为什么不是更小一级：需要多个工作流和聚合验收
为什么不是 Project：只有一个独立能力和一个聚合验收边界，已排除 WS-P01 至 WS-P04
变更类型：Feature
执行拓扑：尚未选择
```

推荐紧凑显示为 `Full · Capability · Feature`。不要使用 `Full-Feature`，因为 Feature 是变更类型，不是规模。

把门禁等级写入 CLI `mode.json`；把工作规模、固定代表说明、当前任务说明和变更类型先写入根级 `task-registry.json` 的任务条目并把投影标为 `PENDING`，再刷新 `workspace-overview.md`，把完整工作规模判定记录投影到任务内或冻结前 staging 的 `development-overview.md`、`progress.md`，最后提交 projection ack 并刷新 `CURRENT` 总纲。CLI 仍只支持 None/Light/Full，不得伪造 CLI 已支持注册表、工作规模或变更类型。`None` 不创建任务包，也不为一次纯回答初始化注册表。

## 规划产物

| 工作规模 | 冻结授权 | 人可读规划 | 进度要求 |
| --- | --- | --- | --- |
| N/A | None，无任务包 | 无 | 无 |
| Micro | Light 简报；命中硬条件时使用 Full baseline | 精简 overview | 一个 T 和适用 SOP |
| Task | Full baseline | overview + 完整 R/A/T 索引 | 全部 T 和 SOP |
| Capability | Full baseline | overview + 工作流、依赖、集成计划 | 工作流、全部 T 和 SOP |
| Project | Full baseline | 开发总纲 + `rounds/planning/project-plan.md` | M/W/T 和全部 SOP |

`Capability` 必须把完整能力拆成可独立验证的 T，并说明聚合验收；`Project` 进一步按 [project-planning.md](project-planning.md) 执行规划质量门禁。

## 升级与续接

- 分析发现规模更大时：`Micro → Task → Capability → Project` 单向升级，并在请求确认前补齐对应产物；
- 真实 diff 让 Light 命中 Full 时：停止验收，升级门禁等级并补齐 Full 授权；工作规模按真实结构复核；
- 冻结后新增工作流、能力、里程碑、服务或验收：按 `REVISE_CURRENT`，不能只改规模字段；
- 后续对话恢复原任务时：沿用磁盘记录的三个维度；证据缺失时让用户确认，不从新措辞重新猜测；
- 只有用户明确缩小并重新确认授权时才能降级，且不得删除旧冻结证据。

修复一个 Project 仍是原 Project 的新轮次，不会变成 Micro。生命周期动作和工作规模必须分别记录。

## 组合示例

- “解释这段报错，不改代码”：`None · N/A · N/A`。
- “修正两个文件中的低风险字段映射和测试”：`Light · Micro · Bugfix`。
- “修改一个权限判断中的明显错误”：结构上可能是 `Micro`，但权限命中硬条件，因此是 `Full · Micro · Bugfix`。
- “给现有查询接口增加完整权限能力”：`Full · Task · Feature`。
- “跨订单、库存与通知组件完成订单履约”：`Full · Capability · Feature`。
- “一个提供方与一个消费方围绕同一契约交付单一聚合结果，即使接口很多”：在排除 Project 规则后仍为 `Full · Capability · Feature`。
- “完整交付一个大模块，范围同时覆盖公共契约与提供方、生命周期与幂等规则、消费方编排和十余个接口”：命中 `WS-P01`，并应继续识别能力组与阶段门禁，使用 `Full · Project · Feature`。
- “从零完成账号、订单、结算和报表平台”：`Full · Project · Feature`。
- “迁移整个项目的鉴权协议并兼容多个服务”：变更类型为 `Migration`；只有一个能力级聚合边界时为 `Full · Capability`，命中 `WS-P01` 至 `WS-P04` 时为 `Full · Project`。
